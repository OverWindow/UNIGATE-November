# TOPIQ 결제 유형별 환불·크레딧 차감 사례

운영자가 Stripe에서 **어느 결제를 얼마 환불할지** 결정하면, TOPIQ는 그 주문의 **실결제액과 성공한 환불액**으로 회수할 크레딧을 계산한다. 예를 들어 1,000개를 충전해 600개를 쓴 회원에게 40%를 환불하면 남은 400개로 정산이 끝난다. 같은 회원에게 전액을 환불하면 400개를 즉시 차감하고 600개가 차감 예정으로 남는다. 현금 환불 승인 기준은 [TOPIQ 약관 초안](../frontend-TOPIQ/src/app/settings/terms/page.tsx)에서 확인할 수 있다.

## 계산할 때 보는 세 가지 수량

1. **누적 회수 대상**은 `지금까지 해당 주문에서 지급한 크레딧 × 누적 성공 환불액 ÷ 주문 당시 실결제액`의 소수점 이하를 버린 값이다. 한 주문에서 환불을 여러 번 하면 성공 금액을 먼저 합산한다.
2. **이번에 더 회수할 수량**은 누적 회수 대상에서 이미 순회수한 수량(실제 차감 합계에서 복원 합계를 뺀 값)을 빼서 구한다. 결과가 음수면 초과 차감분을 복원한다.
3. **즉시 차감**은 회원 지갑의 가용 잔액(`보유 − 예약`) 안에서 이뤄진다. 회수 대상 중 당장 차감할 수 없는 수량이 **차감 예정**이다. 예를 들어 보유 100개 중 20개가 예약 중이면 즉시 쓸 수 있는 수량은 80개다.

아래 표에서 금액 단위는 **원**, 크레딧 단위는 **개**다. **가용 잔액**과 **차감 예정**은 각 행의 처리가 끝난 시점 값이다. [계산 및 지갑 정산 코드](../backend/accounts/credits.py)

## 일회성 충전

### 전액 환불과 여러 번의 부분 환불

4,900원에 1,000개를 충전했고 전부 사용 가능하다고 가정한다. 아래 두 시나리오는 각각 같은 초기 상태에서 출발한다. 시나리오 안에서는 위에서 아래로 이어진다.

| 시나리오와 순서 | 이번 환불액 | 누적 성공 환불액 | 누적 회수 대상 | 즉시 차감 | 차감 예정 | 가용 잔액 |
|---|---:|---:|---:|---:|---:|---:|
| 한 번에 전액 환불 | 4,900 | 4,900 | 1,000 | 1,000 | 0 | 0 |
| 나눠 환불 ① 결제액의 30% | 1,470 | 1,470 | 300 | 300 | 0 | 700 |
| 나눠 환불 ② 결제액의 20% 추가 | 980 | 2,450 | 500 | 200 | 0 | 500 |
| 나눠 환불 ③ 남은 금액 전액 | 2,450 | 4,900 | 1,000 | 500 | 0 | 0 |

샌드박스에서 확인한 순서는 **1,470원 → 3,430원**이었다. 첫 환불에서 300개, 두 번째 환불에서 700개가 차감돼 최종 잔액은 0개였다. 이후 판매가가 바뀌어도 이 주문의 계산에는 결제 당시 금액인 4,900원을 쓴다.

## Plus 구독

### 1·3·6개월 결제에서 환불하는 달이 다를 때

Plus는 한 청구 회차에 매월 400개씩 지급한다. **환불 시점까지 지급한 달 수**로 현재 회수량을 계산하고, 이후 같은 회차의 월 지급 때마다 누적 회수량을 다시 계산한다. 표의 각 행은 독립 사례다. 이전 환불·사용·예약·다른 잔액이 없어 즉시 전량 회수할 수 있고, 모든 행의 차감 예정은 0개다. 마지막 열은 환불 비율이 그대로일 때의 값이다.

| 결제 주기와 환불 시점 | 실결제액 | 이번 환불액(누적과 동일) | 그때까지 지급 | 즉시 차감 | 가용 잔액 | 남은 달의 순지급 |
|---|---:|---:|---:|---:|---:|---|
| 1개월 · 첫 달 절반 환불 | 9,900 | 4,950 | 400 | 200 | 200 | 지급 완료 |
| 1개월 · 첫 달 전액 환불 | 9,900 | 9,900 | 400 | 400 | 0 | 지급 완료 |
| 3개월 · 첫 달 절반 환불 | 23,900 | 11,950 | 400 | 200 | 200 | 2개월 × 200 |
| 3개월 · 둘째 달 전액 환불 | 23,900 | 23,900 | 800 | 800 | 0 | 1개월 × 0 |
| 3개월 · 마지막 달 25% 환불 | 23,900 | 5,975 | 1,200 | 300 | 900 | 지급 완료 |
| 6개월 · 첫 달 전액 환불 | 43,900 | 43,900 | 400 | 400 | 0 | 5개월 × 0 |
| 6개월 · 셋째 달 25% 환불 | 43,900 | 10,975 | 1,200 | 300 | 900 | 3개월 × 300 |
| 6개월 · 마지막 달 절반 환불 | 43,900 | 21,950 | 2,400 | 1,200 | 1,200 | 지급 완료 |

**소수점 내림으로 월별 차감량이 1개씩 달라질 수 있다.** 3개월 결제 23,900원에서 첫 달에 8,000원을 환불하면, 각 달의 누적 회수 대상은 133개 → 267개 → 401개다. 각 달에 지급한 400개에서 실제로 회수하는 양은 133개 → 134개 → 134개이고, 순지급량은 **267개 → 266개 → 266개**다. 거래 내역에서 월별 지급과 환불 차감을 함께 보면 이 수량을 확인할 수 있다.

### 첫 결제, 갱신 결제, 구독 해지

3개월짜리 첫 청구서에서 받은 1,200개를 모두 보유한 상태에서 **두 번째 청구서 23,900원**을 환불하는 예시다. 추가 사용이나 예약은 없다. 표의 지급·환불액은 두 번째 청구서 기준이고, 가용 잔액은 두 회차를 합친 회원 지갑 기준이다.

| 두 번째 회차에서 일어난 일 | 이번 환불액 | 누적 성공 환불액 | 누적 지급 | 이번 즉시 차감 | 차감 예정 | 가용 잔액 |
|---|---:|---:|---:|---:|---:|---:|
| 회차 시작 전 갱신 결제분 50% 환불 | 11,950 | 11,950 | 0 | 0 | 0 | 1,200 |
| 회차 시작, 첫 달 400개 지급 | 0 | 11,950 | 400 | 200 | 0 | 1,400 |
| 둘째 달 400개 지급 | 0 | 11,950 | 800 | 200 | 0 | 1,600 |
| 남은 결제액도 전액 환불 | 11,950 | 23,900 | 800 | 400 | 0 | 1,200 |
| 셋째 달 400개 지급 | 0 | 23,900 | 1,200 | 400 | 0 | 1,200 |

첫 청구서의 1,200개는 첫 회차의 지급분으로 남는다. **해지만 예약**하면 성공 환불액은 0원이므로 해지 자체로 차감되는 크레딧은 0개다. 반대로 **환불만 실행**하면 해당 청구서의 크레딧을 정산하고, 구독 갱신 여부와 Plus 이용 종료일은 기존 구독 상태를 따른다. 월별 지급 횟수 기록이 없는 구형 Plus 주문은 당시 한 번 지급한 보너스를 기준으로 계산한다. [청구서 처리](../backend/accounts/subscriptions.py) · [Plus 결제·해지 흐름](stripe-credit-payment-flow.md#갱신과-해지)

## 사용량과 예약에 따른 차이

### 같은 충전 주문에서 회원 지갑 상태가 다를 때

각 행은 **4,900원에 1,000개를 충전한 한 주문의 첫 환불**이다. 이번 환불액이 곧 누적 성공 환불액이다. 회수 대상은 주문별로 계산하고, 실제 차감은 다른 충전분·가입 보너스까지 포함한 회원의 전체 가용 잔액에서 처리한다.

| 환불 직전 상황 | 가용 잔액(전) | 이번 환불액 | 회수 대상 | 즉시 차감 | 차감 예정 | 가용 잔액(후) |
|---|---:|---:|---:|---:|---:|---:|
| 600개 사용, 남은 400개에 해당하는 40% 환불 | 400 | 1,960 | 400 | 400 | 0 | 0 |
| 600개 사용, 운영자가 전액 환불 | 400 | 4,900 | 1,000 | 400 | 600 | 0 |
| 1,000개 전부 사용 후 전액 환불 | 0 | 4,900 | 1,000 | 0 | 1,000 | 0 |
| 원주문 잔여 400개와 가입 보너스 100개 보유 | 500 | 4,900 | 1,000 | 500 | 500 | 0 |
| 원주문 잔여 400개와 다른 충전분 1,000개 보유 | 1,400 | 4,900 | 1,000 | 1,000 | 0 | 400 |
| 보유 100개 중 20개가 평가에 예약된 상태에서 30% 환불 | 80 | 1,470 | 300 | 80 | 220 | 0 |

마지막 행에서 **보유 잔액은 20개, 예약은 20개, 가용 잔액은 0개**다. 평가가 성공해 20개를 사용하면 예약분은 평가 비용으로 지출되고 차감 예정 220개가 남는다. 평가 예약이 해제되면 20개를 환불분으로 회수해 차감 예정이 200개로 줄어든다.

### 여러 주문에 차감 예정분이 쌓일 때

1,000개씩 지급한 4,900원 충전 주문 두 건이 있고, 고객은 2,000개를 모두 썼다. 주문 A가 B보다 먼저 생성됐다. B를 먼저 1,470원 환불하고 A를 나중에 1,960원 환불해도, 새 가용 잔액은 **주문 생성 시각이 오래된 A부터** 회수한다.

| 순서 | 이번 적립 | 이번 즉시 차감 | A 차감 예정 | B 차감 예정 | 가용 잔액 |
|---|---:|---|---:|---:|---:|
| B에서 30% 환불 성공 | 0 | 0 | 0 | 300 | 0 |
| A에서 40% 환불 성공 | 0 | 0 | 400 | 300 | 0 |
| 관리자 지급 500개 | 500 | A 400개와 B 100개 | 0 | 200 | 0 |
| 관리자 지급 250개 | 250 | B 200개 | 0 | 0 | 50 |

회원은 `/credits`에서 실제 거래를 **환불 차감** 또는 **환불 복원**으로 확인할 수 있다. **차감 예정**은 아직 회수할 수량이다. 위 표의 두 번째 행에서 잔액 API의 `available`은 0, `pendingRefundCredits`는 두 주문의 합계인 700이다. [회원 잔액·거래 내역 API](../backend/writing/views.py)

## 환불 상태와 실패 복원

4,900원·1,000개 주문에서 1,470원(30%) 환불을 신청한 예시다. 시작 지갑은 보유 100개, 예약 20개, 가용 80개다. 아래 행은 순서대로 이어진다.

| 사건 | 누적 성공 환불액 | 이번 환불 차감 | 이번 복원 | 차감 예정 | 예약 잔액 | 가용 잔액 |
|---|---:|---:|---:|---:|---:|---:|
| Stripe에서 환불 대기 중 | 0 | 0 | 0 | 0 | 20 | 80 |
| 1,470원 환불 성공 | 1,470 | 80 | 0 | 220 | 20 | 0 |
| 같은 성공 알림 재수신 | 1,470 | 0 | 0 | 220 | 20 | 0 |
| 평가 예약 20개 해제 | 1,470 | 20 | 0 | 200 | 0 | 0 |
| 관리자 지급 50개 | 1,470 | 50 | 0 | 150 | 0 | 0 |
| Stripe에서 해당 환불이 최종 실패로 변경 | 0 | 0 | 150 | 0 | 0 | 150 |
| 실패 이후 과거 성공 알림이 늦게 도착 | 0 | 0 | 0 | 0 | 0 | 150 |

실패 시 실제로 회수한 **80 + 20 + 50 = 150개**를 복원하고, 남아 있던 차감 예정 150개는 해제한다. Stripe에서 최신 환불 상태를 다시 조회하므로 같은 알림이나 늦은 알림도 최종 상태를 따른다. [환불 상태 처리](../backend/accounts/refunds.py) · [예약 해제·복원 테스트](../backend/accounts/tests/test_credit_refunds.py)

| 그 밖의 상황 | 지갑에서 확인할 결과 |
|---|---|
| 대기하던 1,470원 환불이 성공 전에 취소되거나 실패 | 성공 환불액 0원. 최초 가용 80개, 예약 20개 그대로이며 차감·복원·차감 예정은 모두 0개다. |
| 같은 주문에 성공한 환불 두 건 중 한 건만 실패 | 미사용 1,000개에서 1,470원과 980원을 환불하면 500개가 남는다. 980원 건만 실패하면 성공액은 1,470원, 회수 대상은 300개다. 200개 복원 후 가용 잔액은 700개다. |
| 전액 환불 알림이 일회성 주문의 적립 알림보다 먼저 도착 | 시작 잔액 0개인 회원이라면 주문 적립 전 가용 0개, 적립 처리 시 유료 충전 +1,000개와 환불 차감 −1,000개, 최종 가용 0개다. |
| 결제창을 닫고 미결제 상태로 만료 | 실결제액과 지급량이 모두 0이다. 환불로 차감할 크레딧도 0개다. |
| 같은 Stripe 계정의 다른 상품 환불, 또는 원주문과 통화·금액이 불일치 | 다른 상품은 건너뛴다. 식별된 TOPIQ 주문과 환불 정보가 맞지 않으면 처리를 거부한다. 두 경우 모두 해당 알림으로 인한 잔액 변동은 0개다. |

## 기존 결제와 도입 시점

자동 정산 대상은 **각 환경에서 `accounts.0012_credit_refunds` 마이그레이션을 적용한 시점부터 Stripe에 생성된 환불**이다. 환불 생성 시점으로 판정하므로 알림이 뒤늦게 도착해도 기준은 같다.

| 주문과 환불의 시점 | 4,900원·1,000개 미사용 주문을 전액 환불한 예 |
|---|---|
| 도입 전 결제, 도입 후 환불 생성 | 기존 Checkout 세션으로 원주문을 확인하고 1,000개를 차감한다. 최종 가용 0개, 차감 예정 0개다. Plus는 해당 청구서로 회차를 찾는다. |
| 도입 전 환불 생성, 도입 후 알림 재전송 | 이 알림으로 자동 차감되는 수량은 0개다. 이전에 운영자가 수동 정산한 잔액도 그대로 유지된다. |
